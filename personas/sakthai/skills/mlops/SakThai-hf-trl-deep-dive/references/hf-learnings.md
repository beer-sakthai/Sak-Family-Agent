### 1. TRL v1: A New Foundation (March 2026)

TRL v1.0.0 was a **major architectural rewrite** — not just a version bump. The library split into three distinct layers:

| Layer | Purpose | Key Classes |
|-------|---------|-------------|
| **Core** | Algorithm implementations and loss functions | `loss_dpo()`, `loss_grpo()`, `loss_kto()`, etc. |
| **Trainer** | Training orchestration (HF Trainer subclass) | All `*Trainer` classes |
| **Config** | Configuration and hyperparameters | All `*Config` classes + `TrainingArguments` |

Key improvements in TRL v1:
- **KTO graduated from experimental to stable** (no longer 🧪)
- **New trainers added**: RLOO (Reinforce Leave-One-Out), NashMD (Nash Learning Mirror Descent), XPO (Exploit-Explore), BCO (Binary Cross-Entropy Optimization), PRM (Process Reward Model), GKD (Generalized Knowledge Distillation), MiniLLM
- **Multi-environment agentic RL** for GRPOTrainer
- **VLM alignment** support (vision-language models)
- **OpenEnv and Harbor** integrations for sandboxed evaluation
- **Loss function refactoring** — all losses are now standalone functions callable without a trainer
- **vLLM ⚡️ unified** — common vLLM backend shared across all online trainers

Current version: **TRL v1.9.0** (as of July 2026)

### 2. Complete Trainer Taxonomy (v1.9.0)

TRL now organizes trainers into **4 categories**:

#### 2.1 Online Methods (RL-based, generate during training)

| Trainer | Stable? | vLLM ⚡️ | Description |
|---------|---------|----------|-------------|
| **GRPOTrainer** | ✅ Stable | ⚡️ | Group Relative Policy Optimization — multi-reward, no value function |
| **RLOOTrainer** | ✅ Stable | ⚡️ | REINFORCE Leave-One-Out — variance-reduced REINFORCE |
| **OnlineDPOTrainer** | 🧪 | ⚡️ | Online DPO — generate chosen/rejected on-policy during training |
| **NashMDTrainer** | 🧪 | ⚡️ | Nash Learning Mirror Descent — game-theoretic alignment |
| **PPOTrainer** | 🧪 | ❌ | Classic PPO (requires value head model + reward model) |
| **XPOTrainer** | 🧪 | ⚡️ | Exploit-Explore — exploration-aware policy optimization |

**Key insight:** GRPO and RLOO are the workhorses. PPO is now 🧪 (experimental/stale) because GRPO supersedes it for most use cases.

#### 2.2 Offline Methods (static dataset, no generation during training)

| Trainer | Stable? | vLLM | Description |
|---------|---------|------|-------------|
| **SFTTrainer** | ✅ Stable | ❌ | Supervised Fine-Tuning — always the first step |
| **DPOTrainer** | ✅ Stable | ❌ | Direct Preference Optimization — gold standard alignment |
| **KTOTrainer** | ✅ Stable | ❌ | Kahneman-Tversky Optimization — works with unpaired data |
| **BCOTrainer** | 🧪 | ❌ | Binary Cross-Entropy Optimization — BCO variant |
| **CPOTrainer** | 🧪 | ❌ | Contrastive Preference Optimization — CPO algorithm |
| **ORPOTrainer** | 🧪 | ❌ | Odds Ratio Preference Optimization — reference-free |

#### 2.3 Reward Modeling

| Trainer | Stable? | Description |
|---------|---------|-------------|
| **RewardTrainer** | ✅ Stable | Classic Bradley-Terry reward model training |
| **PRMTrainer** | 🧪 | Process Reward Model — step-by-step reward for reasoning |

#### 2.4 Knowledge Distillation

| Trainer | Stable? | Description |
|---------|---------|-------------|
| **GKDTrainer** | 🧪 | Generalized Knowledge Distillation — student-teacher paradigm |
| **MiniLLMTrainer** | 🧪 | MiniLLM — generative distillation from large to small |

### 3. GRPOTrainer Deep-Dive

#### 3.1 Four-Step Algorithm

GRPO is an online algorithm that improves iteratively using data generated by the model itself:

1. **Generate completions** — For each prompt, sample $G$ completions $\{o_1, o_2, ..., o_G\}$
2. **Compute advantage** — For each completion, compute $A_i = (r_i - \text{mean}(r)) / \text{std}(r)$, where $r_i$ are reward scores
3. **Estimate KL divergence** — $\text{KL}(\pi_\theta || \pi_{\text{ref}})$ to constrain policy updates
4. **Compute loss** — Maximize advantage-weighted policy while minimizing KL penalty

#### 3.2 All 5 Loss Formulations

TRL v1.9.0 supports these `loss_type` options for GRPOTrainer:

| loss_type | Full Name | Key Difference | Status |
|-----------|-----------|----------------|--------|
| `"dapo"` | Decoupled Advantage Policy Optimization | Token-level normalization (mitigates length bias) | **Default** ✅ |
| `"grpo"` | Original Group Relative Policy Optimization | Sample-level normalization | Available |
| `"vespo"` | Varentropy-Scaled Policy Optimization | Adaptive entropy scaling | Available |
| `"sapo"` | Sample Advantage Policy Optimization | Simplified advantage computation | Available |
| `"dr_grpo"` | Dr. GRPO | Dr. GRPO variant | Available |

**Critical insight:** `loss_type="dapo"` is now the TRL default because the original GRPO's sample-level loss under-penalizes longer responses in long-CoT scenarios. DAPO's token-level normalization provides more balanced rewards regardless of response length.

#### 3.3 Multi-Environment Agentic RL

TRL v1's biggest new feature: **per-example environment selection** in GRPOTrainer.

```python
from trl import GRPOTrainer

trainer = GRPOTrainer(
    model=model,
    reward_funcs={
        "math": [accuracy_reward, format_reward],
        "code": [execution_reward, style_reward],
    },
    environment="prompt",  # use prompt-level routing
    args=TrainingArguments(...),
    train_dataset=dataset,  # each row has 'env' column or routing key
)
```

- Each training example can specify which environment/reward set to use
- Environments define their own scoring functions
- Integrates with **Harbor** (sandboxed code execution environment) and **OpenEnv** (open agent evaluation environment)
- Mix multiple task suites in a single training run

#### 3.4 vLLM Integration

GRPOTrainer (and all ⚡️-marked online trainers) use vLLM for fast rollout generation:

```
┌─────────────────────────────────────────┐
│              GPU Memory                  │
├──────────────────┬──────────────────────┤
│  Training model  │   vLLM engine         │
│  (TRL Trainer)   │   (rollout gen)       │
├──────────────────┴──────────────────────┤
│  Co-located mode (vllm_device="cuda:0") │
│  OR                                      │
│  Separate GPU (vllm_device="cuda:1")    │
└─────────────────────────────────────────┘
```

**Co-location** (vLLM on same GPU as training) was a major breakthrough — no GPU left behind. Reserve memory via `vllm_gpu_memory_utilization` (default 0.3).

#### 3.5 Liger Kernel Integration

Liger Kernel fuses GRPO operations for faster training:
- Fused KL estimation + loss computation
- Reduces memory by ~40% for GRPO
- Enable via `pip install liger-kernel` before launching training

#### 3.6 Reward Function Design Patterns

GRPO reward functions receive `(prompts, completions, **kwargs)`:

```python
def accuracy_reward(prompts, completions, **kwargs) -> list[float]:
    """Reward correct final answers."""
    rewards = []
    for prompt, completion in zip(prompts, completions):
        answer = extract_answer(completion)
        expected = extract_expected(prompt)
        rewards.append(1.0 if answer == expected else 0.0)
    return rewards

def format_reward(prompts, completions, **kwargs) -> list[float]:
    """Reward adherence to output format."""
    rewards = []
    for completion in completions:
        # Check XML tags or markdown structure
        rewards.append(0.5 if "<answer>" in completion else 0.0)
    return rewards

# Multi-task reward sets can be passed as dict:
reward_funcs = {"reasoning": [accuracy_reward, format_reward],
                "code": [execution_reward]}
```

Best practices:
- Return raw float rewards (no scaling) — GRPO normalizes within the group
- Use multiple reward functions for complex behaviors
- Reward functions must be stateless (no random seed dependence)
- Async reward computation is supported for slower metrics (code execution, LLM-as-judge)

### 4. GT — KTOTrainer (Now Stable)

KTO graduates to the **stable API** in TRL v1. No longer experimental.

**What makes KTO special:** Unlike DPO which requires paired chosen/rejected data, KTO only needs a completion + binary label (good/bad). This means:
- Train on data where you only have positive examples (e.g., good outputs from production)
- Train on implicit feedback (clicks, likes, thumbs-up)
- Much cheaper data collection than DPO

```python
from trl import KTOTrainer

# Dataset: prompt, completion, label (True=desirable, False=undesirable)
kto_trainer = KTOTrainer(
    model=model,
    ref_model=ref_model,
    args=TrainingArguments(output_dir="./kto-model", ...),
    train_dataset=kto_dataset,  # {"prompt": ..., "completion": ..., "label": bool}
)
kto_trainer.train()
```

**Loss function comparison:**
| Method | Data Required | Reference Model | Alignment Signal |
|--------|--------------|-----------------|------------------|
| DPO | Chosen + rejected | Yes | Relative preference |
| KTO | Completion + label | Yes | Binary desirability |
| ORPO | Chosen + rejected | No | Odds-ratio implicit |
| CPO | Chosen + rejected | No | Contrastive implicit |

### 5. New Online Trainers (TRL v1 Additions)

#### 5.1 RLOOTrainer — REINFORCE Leave-One-Out

A simpler alternative to GRPO that uses leave-one-out variance reduction instead of group normalization. Useful when your reward distribution is naturally non-Gaussian.

- ⚡️ vLLM support for fast rollouts
- No value function model needed
- Lower variance than vanilla REINFORCE

#### 5.2 OnlineDPOTrainer — On-Policy DPO (🧪)

Generates chosen/rejected pairs on-policy during training rather than using a static dataset. This aligns DPO closer to true RL-by-preference.

- ⚡️ vLLM for generation
- Higher computational cost but potentially better alignment
- Requires careful reward model or LLM-as-judge

#### 5.3 NashMDTrainer — Nash Learning Mirror Descent (🧪)

Game-theoretic approach where policy and opponent play a Nash equilibrium-seeking game. Theoretically grounded for complex preference structures.

- ⚡️ vLLM support
- Best for multi-dimensional preference learning
- Higher stability but more hyperparameters

#### 5.4 XPOTrainer — Exploit-Explore (🧪)

Combines exploitation (preference optimization) with exploration (novelty-seeking) for broader coverage of the response space.

- ⚡️ vLLM support
- Good for creative tasks where diversity matters

### 6. Knowledge Distillation Trainers (New)

#### 6.1 GKDTrainer — Generalized Knowledge Distillation

Standard KL-divergence-based distillation from teacher to student:

```python
from trl import GKDTrainer

gkd_trainer = GKDTrainer(
    model=student_model,
    teacher_model=teacher_model,  # frozen during training
    args=TrainingArguments(output_dir="./gkd-model", ...),
    train_dataset=dataset,
)
gkd_trainer.train()
```

#### 6.2 MiniLLMTrainer — Generative Distillation

Sequence-level distillation that trains the student to match the teacher's generation distribution, not just token-level logits.

### 7. TRLPipeline Update

`TRLPipeline` still exists and now supports chaining:
- **SFT → DPO** (standard path)
- **SFT → GRPO** (reasoning path)
- **SFT → KTO** (unpaired data path)

However, TRLPipeline is **not well tested with vLLM or distributed training**. For custom setups, use individual trainers.

### 8. Data Format Standards (2026)

#### Standard (Explicit Prompt — Recommended)
```json
{"prompt": "What is 2+2?", "chosen": "4", "rejected": "5"}
```

#### Implicit Prompt
```json
{"chosen": "The sky is blue.", "rejected": "The sky is green."}
```

#### Conversational (Chat Template)
```json
{
  "chosen": [{"role": "user", "content": "Hello"}, {"role": "assistant", "content": "Hi there!"}],
  "rejected": [{"role": "user", "content": "Hello"}, {"role": "assistant", "content": "Go away"}]
}
```

#### GRPO Format
```json
{"prompt": "Solve this math problem: ..."}
```

#### KTO Format
```json
{"prompt": "Hello", "completion": "Hi there!", "label": true}
```

#### SFT Format
```json
{"text": "<|user|>Hello<|assistant|>Hi there!"}
// OR
{"messages": [{"role": "user", "content": "Hello"}, {"role": "assistant", "content": "Hi"}]}
// OR custom columns with formatting_func
```

All trainers accept `peft_config`. Best practices for TRL v1:

```python
peft_config = LoraConfig(

    lora_dropout=0.05, bias="none", task_type="CAUSAL_LM"

# For GRPO/Online methods, LoRA helps reduce memory for both
```

### 10. Memory Optimization Summary (v1.9.0)

| Technique | Savings | When to Use |
|-----------|---------|-------------|
| QLoRA (4-bit) | ~4x | Always for Beer's zero-budget setup |
| Gradient checkpointing | ~30% | Enable unless inference-only |
| Sequence packing (SFT only) | 2-3x throughput | SFT training step |
| fp16/bf16 | ~2x | bf16 preferred for stability |
| Liger Kernel | ~40% GRPO memory | Online training with GRPO |
| vLLM co-location | Shared GPU | Single-GPU online training |
| `remove_unused_columns=True` | Minimal | Always enable |

### 11. Practical Pathways for Beer's Zero-Cost Resources

Beer has no GPU access currently. TRL training requires GPU, but these pathways are relevant for future use:

| Path | Trainers | GPU Needed | Est. Cost | When to Use |
|------|----------|------------|-----------|-------------|
| **SFT with QLoRA** | SFTTrainer | 8-24 GB VRAM | Free Colab/T4 | Always start here |
| **DPO with QLoRA** | DPOTrainer | 12-24 GB VRAM | Free Colab/A10G | After SFT quality check |
| **GRPO mini** | GRPOTrainer | 24+ GB VRAM | Paid GPU needed | Reasoning fine-tuning |
| **KTO with QLoRA** | KTOTrainer | 12-24 GB VRAM | Free Colab/T4 | When only positive labels |
| **HF Jobs** | CLI/TUI | Remote GPU | Free tier limited | Dedicated training runs |

**Zero-cost strategy:**
1. SFT with QLoRA on a free Colab T4 (24GB) — ~2-4 hours
2. DPO with QLoRA on same T4 — ~1-2 hours
3. Evaluate using reward model scoring (evaluate library, no GPU needed)
4. Deploy to HF Spaces (static or free Inference API)

For GRPO/reasoning training, free-tier Colab T4 is insufficient (needs 24GB+ for 1.5B model). Consider HF Jobs if free credits become available, or quantize to 4-bit aggressively.
