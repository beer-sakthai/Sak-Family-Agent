# 1.5B v2 Cron — Sibling Collision Recovery (2026-07-30)

## Timeline

1. **Fetch API data** — `curl` to `/tmp/model_info.json`, parse with `python3` (correct 1.5B data).
2. **Write YAML** — `write_file` to `.eval_results/health-check.yaml` with 1.5B model data.
3. **Sibling overwrite** — 0.5B cron subagent wrote its YAML to the same generic path moments later.
   - `write_file` returned `_warning: "modified by sibling subagent '7821beb8' but this agent never read it"`.
4. **Upload** — `huggingface_hub.upload_file()` sent the FILE ON DISK (now 0.5B data) to the 1.5B repo.
   - Upload succeeded with commit hash — no content check, no identity verification.
5. **Detect** — Local verification script re-read `health-check.yaml` and found `model: Nanthasit/sakthai-context-0.5b-merged`.
6. **Recover** — Re-wrote correct 1.5B YAML, re-uploaded to same path (new commit `977296c`), verified byte-exact match.

## Root Cause

The generic filename `health-check.yaml` is a shared filesystem resource. Multiple cron subagents running concurrently all target it. The last writer wins — and the uploader doesn't re-read to verify identity.

## Lessons

- `write_file` sibling `_warning` is a HARD GATE signal — STOP and verify before any upload.
- Uploading to the correct repo does NOT mean the content is correct.
- The only reliable verification is: fetch the remote file back, parse its model ID, and compare with your target.
- Date-stamped model-specific filenames (`health-check-{slug}-{date}.yaml`) avoid the collision entirely.
- The generic `health-check.yaml` provides zero unique value over the model-specific one — consider skipping it in cron runs.
