### Key detection challenge

The existing `.eval_results/health-check.yaml` on HF still said `merged model` from
Session 1. A consumer reading only the cached health check would be misled. Always
do **fresh file-level detection** (`adapter_model.safetensors` presence, `safetensors`
top-level key in API) rather than trusting an earlier health check on the same repo.

### File size retrieval pattern (LoRA adapters)

API siblings lack `size` field for LoRA repos. Use HTTP HEAD with `x-linked-size`:
```bash
curl -sI "https://huggingface.co/{REPO}/resolve/main/adapter_model.safetensors" \
  -H "Authorization: Bearer $HF_TOKEN" | grep -i x-linked-size
```

### Key findings

1. **Model content can change between cron runs** — always detect type from fresh
   API data, not from earlier health-check cache.
2. **`cardData.base_model` + `base_model:` tag + `base_model:adapter:` tag** —
   LoRA adapters get all three. Cross-reference them for consistency.
3. **Zero downloads expected** — model is ~22 min old. No velocity signal yet.
4. **Xet storage overhead** — `usedStorage` (715 MB) was ~10× current file content
   (73.9 MB). Sign of Git history/LFS pointer overhead.
