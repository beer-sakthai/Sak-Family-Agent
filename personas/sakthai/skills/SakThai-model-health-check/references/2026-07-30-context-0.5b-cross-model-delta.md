# Cross-Model Delta Collision — 2026-07-30

## What happened

During the `sakthai-context-0.5b-merged` health check, step 0.1 fetched
the previous `health-check.yaml` from the stable path. The file showed
**downloads: 5875** — a number that cannot belong to a 0.5B model with
1,370 current downloads. The stable path had been overwritten by a
sibling cron job evaluating a different model earlier in the same cron
window.

## Why it happened

Multiple cron agents (context-1.5b, context-0.5b, context-7b, etc.) all
write to `.eval_results/health-check.yaml` on the same HF repo. The
last one to commit wins. At step 0.1, the previous file on HF was from
whichever model committed last — not necessarily the model being
evaluated now.

This is the **Class A (HF-side commit race)** collision documented in
the parallel-cron pitfalls section.

## The symptom

```
downloads: 5875 -> 1370 (-4505)
```

A 77% drop in downloads is impossible for the same model — downloads
are monotonic. The delta should have been rejected as a cross-model
collision.

## The fix

Before comparing deltas, verify the previous file's model ID matches:

1. Parse `prev_raw` as text (not YAML), iterate lines looking for
   `id: Nanthasit/<something>` — this works with both schemas
   (`target_model.id` and `model.id`).
2. If `prev_id != REPO_ID`, emit an error entry in
   `eval_metadata.changes_since_previous` instead of numeric deltas.
3. If they match, proceed with the normal delta comparison.

This guard is now encoded in step 6.5 of the health-check skill.

## The real delta

The same-model deltas for context-0.5b-merged were actually healthy:

| Metric | Previous | Current | Change |
|--------|----------|---------|--------|
| downloads | 1,370 | 1,370 | 0 (same day) |
| likes | 0 | 0 | 0 |
| lastModified | T21:16:40Z | T21:20:57Z | +4m17s |

The only real delta was a commit (the previous health-check YAML upload
itself) updating `lastModified` by ~4 minutes. No download change in
that window — expected.
